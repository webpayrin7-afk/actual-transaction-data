# 단지 묶음(complex group) 설계안 — 구현 전 검토용

상태: **설계만**. DB 쓰기·코드 변경·배포 없음. 근거 데이터: `dry-run-2026-09-27.json` / `.md`
(스크립트: `scripts/complex-groups/dry-run-complex-groups.mts`, 읽기 전용).

## 1. 문제

국토부 실거래 원자료는 같은 시군구에 이름이 같은 단지를 가르려고 끝에 괄호 지번을 붙인다.
한 단지가 지번(대지)이 둘 이상이면 원자료가 단지를 **지번별로 쪼갠다**.

- `용산파크타워(24-0)` (cx_5a1be94b6a31e36d, 지번 24) — K-apt A14002501 **888세대**, 주거동 1개(표제부) 597세대·40층
- `용산파크타워(24-1)` (cx_ab81babced865643, 지번 24-1) — K-apt 없음, 주거동 1개 291세대·34층
- 597 + 291 = **888** = K-apt 총세대. 사용승인 둘 다 2009-05-15. 같은 본번(24).

지도·상세·3D가 반쪽 단지 두 개로 보인다. 실거래도 둘로 나뉜다(매매 202+95, 전월세 673+461).

증거 규칙 (엄격 — 추정 결합 없음):
- **강한 증거**: 같은 K-apt 코드 · 같은 PNU · 같은 건축물대장 PK ·
  공식 총세대(K-apt 기본정보 또는 총괄표제부) = 멤버 주거동 세대 합. 세대 합 규칙은 30세대 이상, 맞는 멤버 조합이 하나뿐, 공간 증거(같은 본번 또는 150m 안)가 함께 있을 때만 쓴다.
- **약한 증거**: 같은 본번 · 본번 차이 2 이하 · 동 외곽선끼리 150m 안 · 같은 사용승인일 · 사용승인 2년 안.
- **반대 증거**: 400m 넘게 떨어짐 · 사용승인 2년 넘게 차이(사용승인이 없으면 실거래 건축년도 3년 이상 차이) · 서로 다른 K-apt 코드.

CONFIRMED 2건:
1. 용산파크타워 — 공식세대 888 = 597 + 291 · 같은 본번 24 · 같은 사용승인일. 외곽선 거리는 172m라 150m 기준 밖이다.
2. 강서센트레빌3차 (강서구 방화동, 893 / 894-0) — 같은 K-apt A10021866 · 147 = 58 + 89 · 54m · 같은 사용승인일.

LIKELY가 많은 까닭: 122개 묶음에는 K-apt 코드가 하나도 없다. 77개는 멤버가 모두 30세대 미만이라, 같은 건축주가 이웃 필지에 지은 소형 도시형·연립 건물로 보인다.
이 건물들은 법적으로 대지·표제부가 따로다. 같은 단지로 합칠지는 **owner 판단**이다. 자동 병합하지 않는다.

## 3. 용산파크타워 조사

- 마스터에 다른 지번(24-2, 24-3 …)은 없다. 용산동5가(11170-12700) 마스터 행은 이 2건뿐이다.
- 용산구 실거래 `%파크타워%`도 이 두 이름뿐이다(24-0: 매매 202·전월세 673 / 24-1: 매매 95·전월세 461, 건축 2009).
- 건축물대장 표제부(complex_buildings)는 지번당 1개다. `10041100184931`(24, 597세대, 40층), `10041100184602`(24-1, 291세대, 34층).
- GIS 건물(`gis_buildings`)에서 주변 약 400m 안 8층 이상 건물 가운데 '파크타워' 2개뿐이다. PNU `1117012700100240000`(건축면적 11,050㎡), `…0240001`(5,825㎡). 둘 다 공동주택, 사용승인 2009-05-15.
- 결론: 두 멤버 밖에 떨어진 동은 없다. 세대 합이 K-apt와 맞는다(888).
  여러 동으로 보이는 탑은 표제부 하나 안에 묶여 있다(저층부로 이어진 건물). 그래서 3D는 동 단위가 아닌 **덩어리 2개**로 보인다.
- 두 멤버 모두 `complex_building_geometry`가 비어 있다(NO_GEOMETRY). 3D 외곽선은 `gis_buildings` 연결로만 그린다.

## 4. 스키마 (추가만)

초안: `draft-migration-complex-group.sql`

- `complex_group(group_id PK, primary_complex_id UNIQUE, display_name, lawd_cd, bjdong_cd, anchor_lat/lng, evidence_class, evidence_json, rule_version, created_at, updated_at)`
- `complex_group_member(complex_id PK, group_id, role PRIMARY|MEMBER, lot_label, created_at)`
  - 멤버 표를 따로 두면 "단지 → 묶음" 조회가 PK 한 번이다. 지도·상세 요청 경로에서 싸다.
  - JSON 멤버 배열보다 따로 두는 쪽이 낫다. 멤버가 두 묶음에 들어가는 것을 PK가 막는다.
- 대안(가벼움): 대표 단지에 `apt_complex_source_links(source='MOLIT', source_key='11170|용산파크타워(24-1)')`만 추가한다.
  `tx-name-norms.ts`가 이미 MOLIT 링크 이름을 모아 실거래를 합치므로 상세 실거래는 코드 변경 없이 합쳐진다.
  다만 지도에 핀 2개, URL 2개가 남는다. **1단계로 쓸 수 있다.**
- `group_id` = `cg_` + 대표 complex_id 뒤 16자. 결정적이라 다시 돌려도 같은 키가 된다.
- 대표 고르기: K-apt 있는 멤버 > 공식 총세대 큰 멤버 > 주거동 세대 합 큰 멤버 > 매매 건수 많은 멤버.

## 5. 화면별 동작

**지도 핀 (2D, `src/lib/map/map-complexes.ts`)**
- 목록 쿼리에 `LEFT JOIN complex_group_member gm`을 붙인다. `role='MEMBER'` 행은 빼고, PRIMARY 행 하나만 핀이 된다.
- 핀 좌표는 `complex_group.anchor_lat/lng`(멤버 외곽선 전체 가운데)이고, 없으면 대표 단지 앵커를 쓴다.
- 핀 가격·최근 거래는 멤버 전체 `(lawd_cd, apt_name_norm IN (멤버 이름들))`로 읽는다. 이미 lawd별 IN 목록 구조라 이름만 늘면 된다(`idx_tx_lawd_apt_ym` 그대로).
- 이름은 `display_name`("용산파크타워")으로 보인다. `displayAptName`이 이미 괄호를 떼므로 같다.

**3D (`src/lib/complex-3d/read.ts`, `complex_3d_anchor`)**
- 동 목록은 멤버 전체 `complex_buildings`의 합집합이다. GIS 연결은 지금 규칙과 같다(같은 lawd + 대장번호 뒤쪽 + 앵커 1km).
- `complex_3d_anchor`는 묶음 단위로 새로 계산한 값을 대표 행에 둔다. 멤버 행은 그대로 두고 읽지 않는다.
- 부지 경계(`complex_site_boundary`)는 멤버 PNU들을 합친다.

**상세 페이지 (`/apt/[name]`, `get-complex-detail-v1.ts`)**
- 실거래는 `lawd_cd + apt_name_norm` 기준이다. 멤버 이름 목록을 합친다(`complexTxNameNorms`에 묶음 멤버 이름 추가).
- 평형은 같은 전용면적이면 합친다. 세대수는 공식 총세대(K-apt)가 있으면 그것, 없으면 멤버 주거동 세대 합을 쓴다.
- 관리비·학교·생활 스냅숏은 대표 단지 값을 쓴다(멤버 값은 표시하지 않는다).
- 층·동 정보에는 멤버 표제부를 모두 보인다.

**멤버 URL 넘기기**
- `/apt/용산파크타워(24-1)?region=…` → `/apt/용산파크타워?region=…`로 308을 보낸다. 쿼리는 유지한다.
  `proxy`/미들웨어 대신 페이지에서 `getComplexDetailV1`이 멤버를 찾으면 `permanentRedirect()`를 쓴다(Next 16 문서 확인 필요).
- `/complex-3d/[complexId]`에 멤버 id가 오면 대표 id로 넘긴다.
- sitemap은 대표만 내보낸다.

**랭킹·통계**
- `region_complex_rankings` 등은 다음 배치부터 묶음 단위로 계산한다. 멤버는 대표에 합산하고 멤버 행은 만들지 않는다. 지난 스냅숏은 고치지 않는다.

## 6. 적용 절차 (missing-only, 쓰기 최소)

1. dry-run: `dry-run-complex-groups.mts` → JSON. 결과는 CONFIRMED 묶음 수 N, 멤버 수 M.
2. owner 확인: CONFIRMED 목록 + LIKELY 가운데 승인한 묶음(`OWNER_APPROVED`, 목록 파일로 받음).
3. apply 스크립트(`--apply --from=<json>`)는 `INSERT OR IGNORE`만 한다. `complex_group` N행 + `complex_group_member` M행을 한 batch로 넣는다.
   이미 있는 group_id·complex_id는 건너뛴다. 멤버가 다른 묶음에 이미 있으면 **멈추고 보고**한다.
4. 건수 확인: 넣은 행 = N + M인지 본다.
5. 다시 apply → 0행이어야 한다.
6. 파생 값(묶음 3D 앵커, 지도 캐시 `map_complex_recent`)은 해당 묶음만 다시 만든다. 전체를 다시 만들지 않는다.
